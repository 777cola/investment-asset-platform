護城河解剖：一條真的，一條假的 — 甲骨文

護城河要看它保護的是哪一塊收入

核心判斷

甲骨文有兩條護城河，一條是真的，一條是假的。真的那條守住 29% 的收入，假的那條承載 60% 的收入與全部資本支出。把兩條混為一談、籠統地說「甲骨文有護城河」，是這類分析最常見的錯誤。

真護城河：遷移成本是怎麼運作的

資料庫的護城河不在程式碼，而在客戶的資產負債表與監管檔案。銀行更換核心系統，預算通常 2–5 億美元、週期 3–5 年，失敗率極高（歷史上多家銀行換核心系統失敗，損失以十億計）。對 CIO 而言，換掉甲骨文資料庫不是技術決策，而是職業風險決策。只要「不換」不被追責，「換」就永遠不會發生。

這條護城河還有一個反常識的證據：本季資料庫相關業務年增 353%，而 AWS 與 Azure 都接入了 Oracle 資料庫。競爭對手的雲主動相容你的資料庫，說明你的資料庫是客戶不願放棄的資產。這是護城河裡最硬的一種——不是「我比你強」，而是「客戶不允許你消失」。

假護城河：算力為什麼沒有壁壘

拆開來看，OCI 賣的只有三樣：機櫃、電力、網路，而且全是標準品。客戶要遷移到另一家雲，不必重寫應用程式，只要重新部署容器、遷移資料，週期幾週、成本幾百萬美元，與資料庫遷移完全不是同一個量級。切換成本低，定價權就不存在。

甲骨文在 OCI 上的優勢確實存在：阿比林園區單季交付 13.1 萬張 GPU、24 小時驗收、自建燃料電池繞開併網排隊。但這些屬於執行優勢，會被追上；護城河要的是結構優勢，無法被複製。執行優勢在需求緊缺時值錢，供給過剩時一文不值——過剩時客戶不缺供應商，只缺便宜。

護城河的可遷移性：為什麼舊護城河救不了新業務

許多人會說：甲骨文握有資料庫客戶，這些客戶上雲時自然會選用 OCI。這個邏輯聽來順理成章，但資料並不支持——OCI 73.88 億收入中，增量主要來自 AI 實驗室，而非傳統資料庫客戶。傳統客戶上雲時，多數選擇 AWS 或 Azure，因為那裡的應用程式生態更完整。

護城河有其邊界。資料庫的護城河保護的是「資料放在哪裡」，並不保護「算力在哪裡」。在雲時代，這兩件事已經分開——客戶完全可以將資料庫留在 Oracle，把訓練任務放在 AWS。本報告稱此為「護城河不可遷移」，這是理解甲骨文估值的關鍵：老護城河值 3,000 億，新業務須另計。

護城河的折舊：為什麼老護城河在貶值

資料庫護城河並未消失，但正在收窄。原因有二：其一，客戶將新應用部署在雲端，而新應用未必採用 Oracle 資料庫；其二，開源資料庫（PostgreSQL）已在中小客戶羣中取代 Oracle。本季軟體支援收入年減 3%，是這條護城河首次出現負成長。

護城河不會一夜之間消失，而是如冰川般逐步退縮。對估值的影響在於：這塊業務應按「衰退年金」定價，而非「永續成長」定價。以 5% 年衰退率折現，軟體業務價值 2,200 億，而非 3,500 億。

結論

結論：舊業務有真護城河，新業務的護城河是假的。投資含義並非「沒有護城河」，而是「有護城河覆蓋的收入正在萎縮，增長的收入卻沒有護城河」。在這種結構下，估值應為兩塊業務分別估值之和，而非對整體給予成長股倍數。
